02为什么我此前的自检没抓到

方法漏洞

我做的一致性校验只能证明「名字和值自洽」，证明不了「用对了属性」。这两件事是两个维度。

我原先报的「988 条引用 100% 一致」，验的是「变量的定义值 = 该属性在节点上的渲染值」。这条对 fill 和 textColor 各自都成立，所以它会把两处绑定不同、但各自都自洽的节点全部判为通过。同理，我说的「575 个节点 _token 与 fill 两路解析 0 冲突」也只是在比这两个字段，从未与 textColor 对照。

正确做法需要三类校验，我此前只做了第一类：

  • 值一致性（已做）：变量的定义值 = 节点渲染值，用于抓 override / detach。
  • 属性选用（缺失，本次补上）：文字节点必须比对 _token||fill 与 textColor 是否指向同一变量，不同则以 textColor 为准。
  • 模式完整性（部分做）：Light 与 Dark 都要落值，只比 Light 看不出问题——本案两处绑定在日间的色值是相同的。

第 3 条正是这个问题隐蔽的原因：Primitive/Neutral/0 与 Text/Inverse/Primary 日间都是 #FEFEFE，肉眼和截图都分辨不出来，只有切到夜间才暴露。

03已修正的内容

已交付

取数脚本已改，产出多了一个 role 字段和一份文字颜色专项审计，错误路径从「不易察觉」变成「不可能误用」。

核心改动是给每条颜色记录标注用途，而不是只标属性名：

// 旧：一行取到底，文字节点必然取到 fill 的绑定
token = node._token || styles[node.fill]?.token

// 新：按节点类型分流，文字只认 textColor，分段逐段取
if (node.type === 'TEXT') {
  for (const seg of node.textColor ?? []) {
    const token = styles[seg.color]?.token ?? report('MISS', node.id, 'textColor')
  }
} else {
  const token = node._token || styles[node.fill]?.token ?? report('MISS', node.id, 'fill')
}

脚本产出同步变化：

  • node-token-map.json 每条记录新增 role：render 参与渲染可直接用，decoy 是文字节点上 fill/_token 的绑定、不可直接使用。本次 Button 页 render 703 / decoy 310，取错会立刻被这个字段拦住。
  • 新增 text-color-audit.json：逐节点给出 decoyToken、renderToken、mismatch，可直接当回归基线用。
  • 变体契约表里文字色的取值本就走 textColor（Solid / Desktop / Lg-Hug / Default 的文字是 Text/Inverse/Primary），这部分此前是对的，无需改动。

06替换掉我此前那三条约定

文档里原来那三条有一处是错的（第 1 条把文字节点也归到了 fill）。请以这三条为准：

  • 1 名字只从绑定字段取，且要选对属性。文字节点读 node.textColor[].color → styles[ref].token，按段处理；非文字节点读 node._token 或 styles[node.fill].token；描边单独读 strokeColor。
  • 2 拿不到就报错，不许降级。既不许回落到色值反查，也不许回落到另一个属性的 token。MISS 必须带节点 id 与属性名抛出。
  • 3 校验要三类齐全。值一致性（抓 override）、属性选用（文字必须比对 fill 与 textColor）、模式完整性（Light / Dark 都要落值）。只做第一类，本案这种「日间同色、夜间不同」的错误会全部漏过。
