一句话原理为什么这条路能成

设计稿里每个带颜色的地方，引擎早就知道它绑定的是哪个变量。以前拿不到，是因为用的接口不回传绑定字段；换到 getDsl 后，绑定字段和解析值同时返回，前端要的名字由文件直接给出，不存在推算。

// getDsl 返回的样式表，一条 paint 长这样
"paint_38575:81966": {
  "value": ["#0D0D0D"],          // 解析后的色值（当前模式）
  "token": "Button/Solid/Bg/Default"  // ← 设计稿真实绑定的变量名
}

节点上还多给了一个直接字段：node._token 与 node._color 成对出现，一个节点一条，连 paint 引用都不用查。

调用链5 步，纯 stdio，无界面依赖

  1. 拉起 magic-mcp 子进程

    npx -y @mastergo/magic-mcp@latest --token=mg_xxx --url=https://mastergo.com --no-prefix
    --url 文档写“可选”，实际不传会报 无效的URL格式: 。（冒号后为空），源码里是 new URL("") 抛错。--no-prefix 是为了避免工具名带 mcp__ 前缀被客户端丢弃。

  2. MCP 握手

    发 initialize（protocolVersion 2024-11-05）→ 收响应 → 发 notifications/initialized。
    工具清单共 12 个：getDsl / getMeta / getDesignSections / getD2c / getComponentLink / extractSvg …

  3. 调一次 getDsl

    {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
  "name":"getDsl",
  "arguments":{"fileId":"90715591055486",
               "layerId":"38623:91236",
               "format":"json"}}}

    返回约 1.1MB，结构只有三段：styles（70 条样式）/ nodes（节点树）/ components。

  4. 递归节点树，抓所有 paint 引用

    paint 引用在三种形态里出现，必须都抓：
    ① fill: "paint_x" 字符串 · ② strokeColor: "paint_x" · ③ textColor: [{start,end,color:"paint_x"}] 分段数组。
    只抓第 ① 种会漏掉文字与描边（本次漏 425 条）。

  5. 用引用去 styles 查 token，落表

    styles[ref].token 命中即变量名；未命中的标 NO_TOKEN 而不是静默给色值——这条是底线，静默降级正是“给 #0071E3 却应该给 Primitive/Blue/50”的病根。

为什么必须读绑定、不能反查色值真实数据

同一份设计稿里，一个色值对应多个变量名是常态，不是偶发：

按色值反查，只能得到一组候选，无法判定该取哪一个；而读绑定字段，答案由文件直接给出。这两个是本质区别，不是精度差异。

还有一层坑：同一个 primitive 在文件里存在两套命名——Primitive/Neutral/70 与 Color/Primitive/Neutral/70 指向同一个色值，绑定字段会返回哪一种取决于当初挂的是哪个。建议前端在比较时先做 normalize（剥掉开头的 collection 段）。本次 43 个变量名里，有 7 个带 Color/ 前缀、36 个不带，同一 collection 内也不一致。

边界与坑提前说清，避免误判成“工具能读全部”

  • 覆盖无变量名的 25 条不是失败，分四类：①#3D3D3D / #0D0D0D 的状态枚举标题与分组标题（画布标注）；② 最外层 Button 容器的棋盘格渐变底（设计稿背景装饰）；③ COMPONENT_SET 外框的紫色高亮描边 #8358F6；④ Loading 图标内部两个小矩形，描边 paint 解析为空 null。
    而 354 个 COMPONENT / INSTANCE 节点里，未绑变量的颜色是 0 处——组件实体全部有变量名，问题只存在于画布标注与容器装饰上。
  • 模式DSL 只返回当前模式的解析值，不带 Dark。DSL 里 mode / dark 字段出现 0 次。变量名本身是模式无关的，双模式值需要另取一次变量清单（tokens.json 里 95 个变量都带 light/dark 两个值）。也就是说：名字读 DSL，值读变量清单，两件事分开做。
  • 命名token 字符串的 collection 前缀不一致（7 带有 Color/、36 不带），比较前必须 normalize。
  • 门槛需要个人访问令牌；草稿箱里的文件读不到，需移到团队空间或项目下。
  • 几何本页 layoutStyle 的宽高是准的（Lg-Full 500×56、Lg-2 248、Lg-1 168），但同一通道在别处出现过 gap / 圆角的偏移；几何建议用客户端 MCP 或设计稿标注复核，不要单独信 magic-mcp。
  • 漂移规范文件名为“优化中”，token 改名后表会静默失效。每次生成前跑一遍，别把表当静态资产提交进仓库。

落到生成端三段逻辑

// 1. 取节点上的绑定字段（有就直出，不做任何推断）
token = node._token || styles[node.fill]?.token

// 2. 组件节点再叠变体表，补齐状态相关属性
key = [Variant, Breakpoint, Size, State].join("|")
hit = variantTable[key]        // bg / text / border 三处绑定

// 3. 未命中必须上报，不许静默降级成色值
if (!token) report("MISS", node.id, node.name)
判定原则一句话：名字来自绑定字段，值来自变量清单，两者在生成端拼装。任何一步拿不到就报错退出，不猜。
